### B1. ヒグラシが一度も湧かない（ずかん 11/11 が不可能）— 重大

- **何が起きるか**: 31日遊んでもヒグラシは現れない。README（47-48行）と `docs/AUTOPILOT.md:2415` の「ヒグラシ（夕方のみ・40%）が最難関」は、実際には「入手不可」。図鑑の「ぜんぶ そろった。」（704行）も出ない。
- **場所**: `scripts/SummerMain.cs:545-553`（時間帯が変わったときだけ湧かせる）、`:1432`（`_hour >= FromHour` で候補を絞る）、`:1649`（`PhaseOfHour` は 11 と 16 で切り替わる）、`:60`（ヒグラシ FromHour=17）。
- **原因**: セミの再配置は 8:00 / 11:00 / 16:00 の3回しか起きない。16:00 時点では `_hour(≈16.0) < 17` なのでヒグラシは候補に入らず、以後 19:00 まで再配置が無い。同じ理由で、アブラゼミ・ミンミンゼミ（10〜）は 10〜11 時に、ツクツクボウシ（15〜）は 15〜16 時に居ない。ずかんのヒント（652行「10〜17じ」）と実態がずれる。
  検査で `StartHour=17.4`（`test/Festival.cs:17`）から始めた場合だけ 17 時台の候補で湧くので、気づかれなかった。
- **最小の直し方**: 湧かせる時刻の区切りを音の時間帯（`PhaseOfHour`、3 区分＝`_cicadaVoices` の添字）から分離し、「名指しの文」は音の時間帯が変わったときだけ出す。

```csharp
// 湧かせる区切り。8 / 9:30 / 11 / 16 / 17（甲虫の朝夕とヒグラシの 17 時を含む）
private int SpawnSlot() => _hour < 9.5 ? 0 : _hour < 11.0 ? 1 : _hour < 16.0 ? 2 : _hour < 17.0 ? 3 : 4;

{

        ShowMessage(_weather == Weather.Rainy ? "雨の おとが かわった……" : $"{_phaseSpecies}が 鳴きはじめた。", 3.0);
}
```

`signature`（1442-1453）は「前の候補に無かった種」を優先するので、17:00 の再配置では自然にヒグラシが名指しされる。ただし `_prevPool` の更新を「音の時間帯が変わったときだけ」にしないと 9:30 の再配置で前の候補が上書きされ、11:00 の名指しが狂う点に注意。

## 5. 重複・整理の提案

- **R1 「プレイヤーがある地点の近くにいる」判定が 8 通り**。2D 距離の同じ式（`new Vector2(_player.Position.X, _player.Position.Z).DistanceTo(...)`）が `NearShop`(2364) / `NearestFolk`(2206) / `AtAsagao`(2286) / `AtRadio`(2161) / 十円（**1377 と 2274 に同じリテラル 1.9 が 2 回**）/ `CheckDiscovery`(2517) / `AtPond`(1900) に散っている。3D 版が `NearestCicada`(1887) / `CheckStartle`(2001)。
  `private Vector2 PlayerXZ()` と `private bool Near(Vector2 at, float range)` を置き、`CoinRange = 1.9f` を定数化する。
- **R2 相互作用の優先順位が 2 か所に別々の順で書かれている**。`UpdateMessages`（1356-1404: 店 → 人 → あさがお → 十円 → 台 → 池 → セミ）と `_Process`（554-567: 台 → 十円 → 人 → あさがお → 店 → 池 → セミ）。B13 の「1 押し 1 相互作用」を入れるなら、「いま目の前にあるもの」を返す 1 つの列挙関数にまとめ、案内文と実行の両方がそれを使う形にする。
- **R3 `_Ready` の天気設定が二重**。426-427 行で `_weather / Overcast` を決め、495 行の `ApplyWeather()` がまた決める。前者は `SetupAudio`（926, 955 行）が `_weather` を見るために必要なので、`ApplyWeather` を「見た目に反映する」と「日付から決める」に分ければ 1 回で済む。
- **R4 `_talkCount`（262, 2094, 2130, 2391）は保存・復元されるが、どこにも表示されない**。結末で数えるつもりだったなら `PlayEnding` に足す。不要なら消す（セーブ項目も減る）。
- **R5 `FromSet`（2072）があるのに `collected / found` は手書きの foreach（2084-2089）**。3 つとも `FromSet` に。
- **R6 null ガードの不揃い**。`UpdateAsagao` は `_asagaoVine` だけ確認し（2182）、`_asagaoBuds / _asagaoFlowers`（2197-2200）は確認しない。今のビルダーでは同時に作られるので落ちないが、他の `GetNodeOrNull` と方針を揃える（全部ガードするか、`GetNode` にして「無ければ起動時に落とす」に倒す）。
- **R7 `Frozen` を触る場所が 5 つ**（タイトル 505 / ずかん 663 / 導入 768,798 / EndDay 2620,2662 / 店 2372,2398,2444,2468,2474）。「誰が固めているか」を持たないので、店を開いたままずかんを開く（B3）のような重なりで解除順が壊れやすい。理由付きの `HashSet<string> _freezeReasons` を 1 つ置き、`Frozen = _freezeReasons.Count > 0` にすると B3 系の再発を防げる。
- **R8 無意味な式・重複コメント**。`SapTree + new Vector3(0f, 0f, 0f)`（1673）、`<summary>` の二重（1651-1652、2242-2248）。
- **R9 UpdateMessages の「近づくと出る案内」は ShowMessage を通らない**ので、`DEBUG_MSG` の検出（1323-1328）の対象外。案内が独白を隠す方向の上書きは起きない設計だが、逆に独白のタイマーが切れた瞬間に案内へ戻るので、5 秒の独白の直後に「◯◯　スペースで はなす」が被る。検出の網から外れていることは知っておく。
